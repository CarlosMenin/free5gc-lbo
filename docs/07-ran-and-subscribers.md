# 7. Subscribers and RAN emulation

## 7.1 Subscriber provisioning

free5GC does not keep subscribers in a single collection. Each UE is described
by eight documents in eight MongoDB collections:

| Collection | Content |
| --- | --- |
| `subscriptionData.authenticationData.authenticationSubscription` | Key, OPc, sequence number, authentication method |
| `subscriptionData.authenticationData.webAuthenticationSubscription` | Copy used by the web console to display and edit the subscriber |
| `subscriptionData.provisionedData.amData` | Subscribed slices and UE AMBR |
| `subscriptionData.provisionedData.smData` | DNN configuration: session type, QoS profile, session AMBR |
| `subscriptionData.provisionedData.smfSelectionSubscriptionData` | DNNs allowed per slice |
| `policyData.ues.amData` | Access and mobility policy data |
| `policyData.ues.smData` | Session policy data per slice and DNN |
| `subscriptionData.identityData` | Identifiers of the UE |

Subscribers can be created one at a time in the web console
(`http://<node>:30500`). For more than a few UEs,
`scripts/provision-subscribers.py` writes the same documents directly:

```bash
kubectl -n free5gc port-forward svc/mongo 27017:27017 &
python3 scripts/provision-subscribers.py --count 5 --clean
```

The script creates `--count` subscribers with sequential IMSIs starting at
`--imsi-base` (default `208930000000000`), all with the key and OPc configured
in the UE of `manifests/ran/ueransim.yaml`, in slice SST 1 / SD `010203` and DNN
`internet`. `--clean` removes the existing subscribers first.

Points that are easy to get wrong when writing these documents by hand, and
that the script reproduces as the web console of v4.2.3 writes them:

- the authentication collection stores `encPermanentKey` and `encOpcKey` (in
  clear, despite the prefix), not the `permanentKey`/`opc` objects that the web
  console API receives;
- `sequenceNumber` is an object (`sqnScheme`, `sqn`), not a string;
- the slice keys in `smfSelectionSubscriptionData` and in `policyData.ues.smData`
  are the SST in two hexadecimal digits followed by the SD: SST 1 and SD
  `010203` give `01010203`;
- `amData` and `authenticationSubscription` carry a `tenantId`.

The `tenantId` is generated by the web console on its first start and is read
by the script from the `tenantData` collection. The web console must therefore
have started once before the script is run; otherwise the script stops with a
message.

A single DNN is provisioned. The breakout is decided per destination inside
the session, not by a dedicated DNN; adding a second DNN that is not declared
in the SMF configuration would make the corresponding session be rejected.

**Difference from subscribers created in the web console.** The web console
also writes charging data for each subscriber; the script does not. With
charging data present, the PCF sends a default PCC rule for the session and
the SMF builds the default data path from the global `links` of its
configuration rather than from the `topology` of the UE routing group. In this
repository the two describe the same path, so the difference has no effect. It
becomes relevant when a group topology is meant to differ from the global
links (see [11-extensions.md](11-extensions.md), section 11.4).

## 7.2 UERANSIM

`manifests/ran/ueransim.yaml` deploys one pod with three containers that share
the pod network namespace:

| Container | Image | Function |
| --- | --- | --- |
| `gnb` | `free5gc/ueransim:v4.2.3` | `nr-gnb`: N2 towards the AMF, N3 towards the UPF |
| `ue` | `free5gc/ueransim:v4.2.3` | `nr-ue`: registers, establishes the PDU session, creates `uesimtun0` |
| `probe` | `python:3.12-slim` | Idle container from which the traffic probe is run |

### gNB configuration

```yaml
linkIp: 127.0.0.1
ngapIp: '@POD_IP@'
gtpIp: '@POD_IP@'
amfConfigs:
  - address: amf.free5gc.svc.cluster.local
    port: 38412
slices:
  - sst: 0x1
    sd: 0x010203
```

- `linkIp` is the address of the simulated radio link. The gNB and the UE are
  in the same pod, so the link stays on the loopback interface.
- `ngapIp` and `gtpIp` must be the address of the pod. UERANSIM does not expand
  environment variables in its configuration, so the container replaces the
  marker `@POD_IP@` with the pod address (obtained through the Downward API)
  before starting `nr-gnb`.
- The AMF is addressed by its Service FQDN.
- `tac`, `mcc` and `mnc` must match the AMF configuration.

### UE configuration

- `supi` is the first IMSI. It must be provisioned (section 7.1) and listed in
  the `members` of the UE routing file.
- `key`, `op` and `opType: 'OPC'` are the credentials written by the
  provisioning script.
- The session requests DNN `internet` in slice SST 1 / SD `010203`.
- **`useNamespace: false`** is required. With `true`, UERANSIM creates the
  tunnel interface in a dedicated network namespace, and the `probe` container
  would not see it.

The `ue` container waits for the gNB configuration to be rendered and for a few
seconds more before starting, so that the radio link is up when the UE first
tries to register.

### Number of UEs

The number of UEs is set in the manifest, not by scaling at runtime:

- `NUM_UE` in the `ue` container is the number of sequential IMSIs registered by
  one `nr-ue` process, starting at `supi`. Each UE gets its own tunnel
  interface (`uesimtun0`, `uesimtun1`, ...).
- `replicas` of the StatefulSet is the number of pods.

Every IMSI must be provisioned and listed in the UE routing file
([11-extensions.md](11-extensions.md), section 11.1).

### Sending traffic through the PDU session

Two conditions must hold for traffic to cross the 5G user plane:

1. the socket is **bound to the UE address** (the address of `uesimtun0`);
2. the destination is **routed through the tunnel interface**.

```bash
kubectl -n free5gc exec free5gc-ueransim-0 -c ue -- ip -4 -o addr show uesimtun0
kubectl -n free5gc exec free5gc-ueransim-0 -c ue -- ip route replace <destination>/32 dev uesimtun0
```

Without them the traffic leaves through the interface of the pod, reaches the
destination over the cluster network, and crosses no UPF. The result is a
working connection with low latency that says nothing about the 5G data path.
`scripts/verify-lbo.py` installs the routes and binds the probe accordingly.

### Note on the choice of emulator

my5G-RANTester does not interoperate with free5GC v4.2.3. The NAS registration
completes, but the PDU session establishment fails while the emulated gNB
decodes the `PDUSessionResourceSetupRequest`:

```
[GNB][NGAP] Error in decode Pdu Session Resource Setup Request Transfer
panic: runtime error: index out of range [0] with length 0
```

The cause is Information Element 126 (`AdditionalUL-NGU-UP-TNLInformation`) of
3GPP TS 38.413, whose type changed between releases. The emulator declares it
as a single transport-layer information element (Release 15), whereas free5GC
v4.2.3 encodes it as a list (Release 16). The decoder of the emulator rejects
the mismatch instead of skipping the element. The UERANSIM build distributed
as `free5gc/ueransim:v4.2.3` decodes the Release 16 form and works without
modification.

## 7.3 Order: subscribers before the RAN

UERANSIM must be started **after** the subscribers are provisioned. If the UE
starts first, the registration is rejected because the subscriber does not
exist, the UE retries a limited number of times (timer T3511, five attempts,
about 45 seconds) and then stops trying. From that point it stays unregistered
even after the subscribers are provisioned, and its log only shows a generic
failure cause.

The correction is to recreate the pod, which starts a new registration:

```bash
kubectl -n free5gc delete pod free5gc-ueransim-0
```

For this reason `scripts/deploy.py up` does not start UERANSIM; it is started
separately with `scripts/deploy.py ran`, after the provisioning.

The state of the UE is read with the UERANSIM command-line client:

```bash
kubectl -n free5gc exec free5gc-ueransim-0 -c ue -- ./nr-cli imsi-208930000000000 -e status
```

A registered UE reports `RM-REGISTERED`. That state alone does not prove that
the core is still serving it: UERANSIM keeps reporting `RM-REGISTERED`, and
keeps the address on the tunnel interface, after the core has been removed or
redeployed. After redeploying the core, the UERANSIM pod must be recreated as
well.
